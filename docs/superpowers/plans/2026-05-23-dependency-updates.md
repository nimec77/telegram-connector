# Dependency Updates Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Project rule (CLAUDE.md):** Claude NEVER creates git commits. Every "Commit" step in this plan means: stage the changes with `git add`, show the user the planned commit message, and let the user run `git commit` themselves.

**Goal:** Bring every direct dependency in `Cargo.toml` (excluding `grammers-*`) to the latest stable version available on crates.io as of 2026-05-23, landed in three independently revertible phases.

**Architecture:** Three sequential phases (patches → non-`rmcp` minors → `rmcp` 1.7), each a single user-managed commit. Verification gate after each phase: `cargo fmt --check && cargo clippy -- -D warnings && cargo test` (config tests serialized with `--test-threads=1`).

**Tech Stack:** Rust nightly (2024 edition), Cargo, `cargo update`. No runtime code changes are expected unless rmcp 1.7 has shifted the macro API surface in Phase C.

**Reference spec:** `docs/superpowers/specs/2026-05-23-dependency-updates-design.md`

---

## File Structure

This plan touches exactly two files plus the test suite:

- **Modify:** `Cargo.toml` — bump version specs.
- **Modify:** `Cargo.lock` — regenerated by `cargo update` / `cargo build`. Not hand-edited.
- **No source-code edits expected** in Phases A and B. Phase C may require call-site edits in `src/mcp/server.rs` if rmcp 1.7 changed the `#[tool_router]` / `#[tool(...)]` / `InitializeResult` API.

## Phase C: `rmcp` 1.6 → 1.7 (isolated)

### Task C1: Pre-bump research — scan rmcp 1.7 changelog

**Files:** none (research-only)

- [ ] **Step 1: Fetch rmcp 1.7 release notes**

Inspect `https://github.com/modelcontextprotocol/rust-sdk/releases` (or the `CHANGELOG.md` in the rust-sdk repo) for the 1.7.0 release notes.

- [ ] **Step 2: Look for breaking-change keywords**

In the 1.7 changelog, grep (visually) for any of:

- `tool_router`
- `tool(` / `#[tool`
- `InitializeResult`
- `with_server_info`
- `with_instructions`
- `ServerCapabilities`
- `BREAKING`

Record any matches as a short list of "potential call sites to verify". If the changelog is empty or trivial (typo fixes, doc updates), proceed directly to Task C2.

### Task C2: Bump `rmcp` in `Cargo.toml`

**Files:**
- Modify: `Cargo.toml`

- [ ] **Step 1: Edit the `rmcp` line**

Change:

```toml
rmcp = { version = "1.6.0", features = ["server"] }
```

to:

```toml
rmcp = { version = "1.7.0", features = ["server"] }
```

- [ ] **Step 2: Run targeted update**

Run: `cargo update -p rmcp -p rmcp-macros`

Expected: lockfile bumps both `rmcp` and `rmcp-macros` to `1.7.0`. If `rmcp-macros` does not resolve to 1.7.0, surface this to the user — version mismatch between `rmcp` and its proc-macro crate will cause `expected version X, found Y` macro-expansion errors.

### Task C3: Build and triage

**Files:** potentially `src/mcp/server.rs` (only if rmcp 1.7 broke an API)

- [ ] **Step 1: Compile**

Run: `cargo build`

Expected outcomes:

- **(A) Clean build:** rmcp 1.7 is API-compatible. Proceed to Task C4.
- **(B) Macro expansion errors** on `#[tool_router]` or `#[tool(...)]`: rmcp moved the macro surface. Inspect the macro's docs at `https://docs.rs/rmcp/1.7.0/rmcp/` for the new attribute syntax. Apply the minimal edit to `src/mcp/server.rs`. Re-run `cargo build`.
- **(C) Type errors on `InitializeResult::new(...).with_server_info(...).with_instructions(...)`:** the builder API changed. Inspect `https://docs.rs/rmcp/1.7.0/rmcp/model/struct.InitializeResult.html` for the current builder, update the call site (likely also in `src/mcp/server.rs`), re-build.

- [ ] **Step 2: If source edits were required, document them inline**

If Task C3 Step 1 required code edits in `src/mcp/server.rs`, the edits must be the minimum needed to compile. Do NOT take the opportunity to refactor surrounding code. If you find yourself touching more than the API-call lines themselves, STOP and ask the user.

### Task C4: Verify Phase C

**Files:** none

- [ ] **Step 1: Run formatter check**

Run: `cargo fmt --check`

Expected: exit code 0. If Task C3 introduced code edits, run `cargo fmt --all` first to format them, then re-run the check.

- [ ] **Step 2: Run clippy with warnings as errors**

Run: `cargo clippy -- -D warnings`

Expected: clean. Pay attention to any `deprecated` warnings on rmcp APIs — these signal an upcoming break we should adapt to even if 1.7 still compiles the old call.

- [ ] **Step 3: Run full test suite**

Run: `cargo test`

Expected: all tests pass. The MCP tool tests under `src/mcp/tests/` exercise every tool via mocks, so they'll catch any regression in how rmcp wires tool dispatch.

- [ ] **Step 4: Run config tests serially**

Run: `cargo test config -- --test-threads=1`

Expected: pass.

- [ ] **Step 5: Smoke test the binary**

Run: `cargo run --bin telegram-mcp -- --help`

Expected: prints the CLI help text without panicking. This catches any runtime initialization failures in rmcp's server setup that the unit tests wouldn't trigger.

### Task C5: Commit Phase C

**Files:**
- Stage: `Cargo.toml`, `Cargo.lock`, and `src/mcp/server.rs` only if it was modified in Task C3.

- [ ] **Step 1: Stage the changes**

Run: `git add Cargo.toml Cargo.lock` and, only if Task C3 modified it, also `git add src/mcp/server.rs`.

- [ ] **Step 2: Show the user the planned commit message and hand off**

If no source edits were required, show:

```

API-compatible bump. No call-site changes needed.
```

If source edits WERE required in `src/mcp/server.rs`, show:

```
chore(deps): bump rmcp 1.6.0 → 1.7.0

Updates <#[tool_router] | #[tool] | InitializeResult>
call sites in src/mcp/server.rs to match rmcp 1.7 API.
```

…with the bracketed placeholder replaced by the actual API that changed. Do NOT run `git commit`. Wait for the user.
