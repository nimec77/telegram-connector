Logs folder: `~/Library/Application Support/telegram-connector/logs`

Issue: tool responses silently lost between connector stdout and client; connector lacks the observability to prove response delivery (v0.5.2)
What happened (from telegram-connector_2026-06-12.log, all times UTC)
A claude.ai session issued get_recent_messages(channel_id="wublockchainenglish", hours_back=168, limit=100). The connector handled it correctly — username resolved to 1534592031, response with 84 messages completed in 546ms at 02:29:07.689. The client never received this response and timed out after 240s. At 02:29:16 (8.3s after the response was written) the log shows input stream terminated → clean shutdown: Claude Desktop closed the connector's stdin.
The connector was respawned at 02:34:39. During the entire 02:34:40–02:58:08 session the log shows zero tool invocations, although the client issued at least two calls in that window (a retry and a check_mcp_status), each timing out client-side at 240s — requests were not being routed to the new process at all. Another input stream terminated / respawn cycle at 02:58:08/02:58:26, after which traffic flowed normally (calls at 02:59, 03:08+ all served in <1.1s).
There are three input stream terminated cycles within ~1 hour (01:58:32, 02:29:16, 02:58:08). The log contains no FloodWait, no ERROR/WARN, no panic. Every request that reached the connector was answered in under ~1.1s, including username-based lookups (identifier: Some("…") resolved in ~550–800ms consistently).
Conclusion
The connector's request handling is healthy. The failure is in the transport path (connector stdout → Claude Desktop bridge → Anthropic backend): one response was produced but lost in transit, and the subsequent bridge session was a zombie that dropped inbound requests. This is likely external to the connector (Desktop bridge / network instability — note the host runs behind a VPN). However, the connector currently cannot prove any of this from its own logs, and two tools log asymmetrically. The work below is hardening + observability so the next incident is diagnosable in one glance, plus a recovery path that avoids re-querying Telegram.
Changes to implement

Symmetric, correlated request/response logging. Every tool must log started and completed (today get_subscribed_channels and check_mcp_status log only started — see log lines at 02:03:40, 02:28:30, 03:08:24). Include the MCP JSON-RPC request id in both entries so started/completed/written records correlate.
Log the actual stdout write. After serializing each response, log: request id, tool name, payload size in bytes, write+flush duration, and success. This is the evidence that distinguishes "connector never answered" from "answer was lost downstream" — the exact ambiguity of this incident.
Detect blocked writes. If a stdout write/flush takes longer than a threshold (e.g. 500ms), emit a WARN with the request id and duration. A stalling pipe means the peer stopped reading — the smoking-gun signature if the Desktop bridge wedges while the process is still alive.
Shutdown context. On input stream terminated, log: session uptime, requests received/responses written counters, seconds since the last successful write, and the ids of any in-flight requests being abandoned.
Zombie-session visibility in check_mcp_status. Add fields: requests_received, responses_written, last_response_write_age_secs, session_started_at. A bridge session that routes nothing becomes instantly visible from the client side.
Cheap response recovery (optional but recommended). Keep a small ring buffer of the last N serialized responses keyed by request id, and expose a get_last_responses(n) debug tool. When a response is lost in transit, the client can re-fetch it without re-hitting Telegram API and without re-spending the rate budget.
Out of connector scope, worth checking separately: Claude Desktop logs around 02:29:16 and 02:58:08 UTC for websocket disconnect/reconnect events. If the bridge dropped the connection while a response was in flight and then failed to route requests to the respawned process for ~24 minutes, that's an upstream bug to report to Anthropic, not something fixable in the connector.

Non-goals / corrections to prior analysis
An earlier hypothesis blamed a FLOOD_WAIT on contacts.resolveUsername slept in-band under a global lock. The log disproves this: no flood waits occurred, username resolution is fast and cached, and the "recovered with a full rate-limiter bucket" observation is explained by a process restart, not a drained penalty. Do not implement flood-wait-specific changes on the basis of this incident (fail-fast flood-wait handling is still reasonable general hygiene, but it is not the fix for this bug).
