# Telegram workspace, hosted services, and live channel posts

**Status** — Workspace specification for 0.27.0, revised 2026-11-20. The original design is archived at `4618221`.

People can run the stdio connector locally or sign into a centrally hosted service and link their own Telegram account. Applications can search, read, and observe that account through an HTTPS API. MCP clients get a separate HTTP service with tools suited to remote use. A Rust application can use the same Telegram operations and live feed in process.

The first hosted milestone has two users, two linked Telegram accounts, search through both hosted interfaces, and a live channel feed through the core and API. A returning listener receives newly published posts from a fresh starting point. History is a separate, explicit read. The implementation also includes a full dependency update.

## Workspace and process ownership

```text
Local MCP client  -> stdio -> telegram-mcp      -> telegram-core -> Telegram
Hosted MCP client -> /mcp  -> telegram-mcp-http ─┐
Direct API client -> /v1 -----------------------┴-> telegram-api -> telegram-core -> Telegram
Live subscriber   <- SSE   <----------------------- telegram-api <- telegram-core <- Telegram
```

| Workspace member | Owns |
|---|---|
| `crates/telegram-core` | Typed account operations, grammers, private session handling, Telegram authorization primitives, account rate limits, deadlines, and the live update reader. |
| `crates/telegram-connector` | The `telegram_connector` library facade and `telegram-mcp` binary. Owns stdio, interactive `--setup`, legacy output, desktop launching, and local file delivery. Install with `cargo install --locked --path crates/telegram-connector`. |
| `crates/telegram-api` | Standalone service. Owns hosted identities, Telegram account links, active sessions, authorization, HTTP routes, OpenAPI, SSE, and service-wide resource limits. |
| `crates/telegram-mcp-http` | Standalone MCP service. Owns MCP discovery, tools, schemas, rendering, delegated API calls, and request cancellation. Its dependency tree must build without grammers or access to a Telegram session directory. |

Use a virtual root Cargo workspace with all four packages under `crates/`. Set `crates/telegram-connector` as the default member for unqualified commands at the workspace root. Keep resolver 3, the existing nightly policy, one root lockfile, workspace lints and shared dependency declarations. Keep transport-specific features on the members that use them. Share neutral HTTP DTOs or MCP rendering helpers in a small library target when a second caller needs them. Keep the stdio facade out of the HTTP gateway's dependency tree. Preserve existing example targets, binary name, config resolution, direct legacy Rust methods, and supported stdio handshakes/output modes. Extend CI, `just`, the dependency-policy fixtures, and version tooling to understand members and release checks for each binary. First-party members can be identified by exact reviewed package paths and workspace membership in the policy checker. Keep the external source and license checks for the rest of the graph. [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html) · [Rust API inventory](rust-api.md) · [Stdio runtime](stdio-runtime.md)

The stdio member retains the package name `telegram-connector`, the `telegram_connector` import path and the `telegram-mcp` binary name. Its manifest supplies the authoritative release version. Align all four first-party package versions for a workspace release and update versioned internal path dependencies with them.

**Deployment choice.** Start with one stateful API instance and one independently restartable HTTP MCP gateway. Embedding grammers in both hosted processes would give a user two session owners, two rate budgets, and two competing update readers. A dedicated process per account provides stronger fault isolation, with additional supervision and memory costs. The account-operation interface allows that change later. Use an exclusive service-data-root lock in the first deployment to prevent a second API instance from opening the same session stores. Local stdio owns a separate session under the local user's config.

## Telegram operations in the core

Expose an account-bound async operations facade above the existing injectable `TelegramClientTrait`. The low-level trait currently leaves charging to its caller. Retain that trait for compatibility and transport mocks. Put all product-facing Telegram operations, including full search fan-out and batch reads, behind the charged facade. A gateway tool invokes one API operation even when that operation makes several Telegram calls. [Client seam](../crates/telegram-core/src/telegram/trait_def.rs) · [Current search orchestration](../crates/telegram-connector/src/mcp/server/impl_search.rs) · [Current media orchestration](../crates/telegram-connector/src/mcp/server/impl_media.rs)

- Move domain validation, account charging, Telegram resolution, common pagination, partial outcomes, and total operation deadlines together. Share account status and limits across requests. Keep option coercion, schema generation, legacy shapes, final JSON-RPC frame sizing, recovery keys, desktop launching, and local file arguments at their respective boundaries.
- Preserve validation before charging and charging before request-initiated RPCs, including username resolution. Keep atomic charging for distinct fan-out channels, existing failed-channel charging, media refunds and send charges. Reserve/refund exactly once, including when final media shaping fails. Carry an explicit operation deadline and cancellation into each asynchronous stage. Both HTTP hops consume a common remaining budget.
- Keep positive decimal string peer IDs, peer namespaces, positive integer message IDs, UTC timestamps, channel-local cursors, album boundaries, byte limits, and typed per-item failures. Preserve search deadline partials and Telegram delivery outcomes. Wire-size-dependent trimming and MCP image blocks belong in the presenter. Extract neutral upload-source, progress, cancellation, and shutdown types where the current sending and media code imports MCP internals. [Tool contract](tool-contract.md) · [Sending](sending.md) · [Media artifacts](media-artifacts.md)
- Add a separate core subscription interface. For example, `account.subscribe_channel_posts(channels, cancellation)` asynchronously returns the per-channel starting positions and an owned receiver of typed posts or a terminal reason. Dropping it unregisters the subscription. An updated binary must still compile against an external read-only implementation of the current client trait.

## Hosted identity, linking, and operations

**Service sign-in and delegation.** Use an existing OAuth authorization server with OIDC sign-in, HTTPS, and two resource audiences, API and MCP. Identify a service user by a stable internal key mapped from verified issuer and subject. Configure a common subject mapping where the provider uses pairwise identities. Use separate `telegram.read`, `telegram.send`, and `telegram.link` scopes. Bind the browser linking flow to the signed-in user with authorization code + PKCE, state, nonce, a secure HTTP-only session cookie and CSRF protection. Direct API clients present API-audience access tokens. The gateway validates the MCP audience and exchanges the incoming credential as an authenticated client for a short-lived API-audience token with the same user and at most the original scopes. The API independently validates issuer, signature, audience, expiry, scopes and account ownership. The gateway gets read/send scopes only. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) · [OAuth token exchange](https://www.rfc-editor.org/rfc/rfc8693)

Implement the identity integration through discovery and configuration. Prove it with a local test issuer, a registered OAuth client and an independent MCP client completing discovery, authorization and a real tool call. Document issuer URL, JWKS rotation, client registration/redirect URIs, exchange credentials and both audiences. Reject exchange results with a changed user or broader scope. A deployment can supply any provider that meets these capabilities. Named provider certification is a deployment choice.

**Account linking.** Serve the account page and linking endpoints from `telegram-api`. Use the operator's Telegram application credentials and the existing phone/code/optional two-factor flow. Start a short-lived challenge bound to the user, accept each step only in its expected state, expire replaced or abandoned attempts, and limit attempts by user and source. Keep codes, passwords and Telegram challenge tokens out of URLs, logs and persistent metadata. Use a separate opaque application challenge ID in route paths. Complete a link only after Telegram has confirmed the account identity. V1 permits one active Telegram link per service user and one service owner per Telegram account. Concurrent or conflicting links fail generically without revealing the other owner. Link administration stays in the account UI/API. [Existing Telegram sign-in](../crates/telegram-core/src/telegram/client/auth.rs) · [Telegram user authorization](https://core.telegram.org/api/auth)

**Storage and revocation.** Persist the principal-to-link mapping, verified Telegram user ID, link state, and a generation identifier in a private service database (SQLite is sufficient for one instance). Allocate a separate private session directory per link generation using server-generated names, on encrypted persistent storage. Reuse the existing session DB/sidecar ownership and permission checks. Enforce ownership and generation on all handles, including uploaded objects, media resources, and requests already waiting for admission. Link activation and retirement must be recoverable across process crashes. On unlink, durably disable the generation first, cancel its work and listeners, invalidate its handles, request Telegram logout, then purge session and temporary data. Retain failed remote revocation as restricted cleanup work and surface pending status. Restart must never reactivate a retired generation. Expiry of one API credential closes that caller's stream without unlinking the account. [Session storage](../crates/telegram-core/src/telegram/session_storage.rs)

If logout fails, quarantine only the old session material for bounded revocation attempts for up to 24 hours. Purge it on confirmed logout or expiry, and tell the user when manual revocation in Telegram's Devices screen is still needed. Permit a fresh verified link using a new authorization and directory once local retirement is committed. Cleanup addresses the retired session exclusively. Retain a non-secret status for the account page after erasure. [Telegram logout](https://core.telegram.org/method/auth.logOut)

**Read grants.** The account page lists the owner's joined channels and lets the owner grant or revoke access per registered client. For an owner's direct personal client, the read grant can cover all eligible joined channels. For a delegated MCP client, the owner selects specific channels. Effective access is the intersection of that grant, deployment policy, token scope and current Telegram access. Carry authenticated client identity through token exchange so the API enforces the originating grant. Apply the same grant to that client's REST reads and SSE. Listing, resolution, history, search, media, counts, pagination and caches must all respect the effective scope. Return the same unavailable response for a foreign and a missing channel. Restrict hosted public directory or global search to a separately granted capability if introduced. A grant change invalidates affected subscriptions and resource reads.

**Send grants.** The owner enables or revokes sending for a client on the account page. Once enabled, that client may send text or media to any supported destination the linked Telegram account can send to, including peers outside the client's read grants. The caller selects the recipient with each send. Apply this rule to both the direct API and the MCP gateway. Bind the send grant to the client and account generation, and check it at admission and immediately before final dispatch. Telegram enforces posting permissions at the destination. Revocation that races an already dispatched send follows the existing delivery-state contract.

**Runtime.** Use a Tokio runtime per binary and a registry keyed by account and generation. Concurrent first requests share one client initialization. An active operation or subscription holds a lease. Evict idle clients, preserving account rate limits across eviction, and start conservatively after a service restart. Keep the number of accounts, in-flight calls, streams, queued bytes, downloads and CPU jobs bounded at both account and service level. Hold registry locks only while updating state. Reject saturated admission before Telegram charging. Unlink, shutdown, failed startup, and idle eviction must terminate the sender and update tasks and release capacity. Stop admission on shutdown and drain against one deadline. The gateway's liveness and the API's readiness must be checkable without contacting a user's Telegram account.

## HTTPS API and HTTP MCP

Publish a versioned OpenAPI contract, including status codes, scopes, request limits, media types and examples. Use JSON over HTTPS for operations, bounded binary bodies for uploads/downloads, and SSE for live events. Axum/Tower with Tokio is the proposed server stack. The API derives the account from authentication. Channels and message IDs in a request select resources inside that account.

| Surface | Initial contract |
|---|---|
| `POST /v1/account/link`, `POST /v1/account/link/{challenge}/code`, `POST /v1/account/link/{challenge}/password`, `DELETE /v1/account/link` | Account linking/unlinking, `telegram.link`. Return the next required step or a terminal state. `GET /v1/account` reports only the caller's linked state and cached account status. |
| `GET` and `PUT /v1/account/grants/{client_id}` | Manage the client's read scope and a single `send_enabled` boolean for the linked account. Require a first-party owner session with `telegram.link`, CSRF protection for browser writes, and an expected revision on updates to prevent a stale tab from restoring revoked access. |
| `POST /v1/messages/search` | Query, explicit channel scope, filters and limit. Return typed messages, pagination, partial/timeout flags and per-channel failures. Include only scopes supported by the caller and deployment. |
| `GET /v1/channels/{id}/messages`, `POST /v1/messages/batch` | Paged channel history and bounded ID lookup. The history route supports the precise stream-to-history handoff below. A batch returns missing or omitted IDs explicitly. |
| `GET /v1/events?channel_id=42&channel_id=73` | Authenticated live feed for one or more distinct joined broadcast channels. The public event contract follows below. |
| Additional reads | Add joined channel listing, info, channel resolution, message links, channel stats, discovery, media and transcription as complete operations. Preserve existing operation-specific eligibility, limits, costs, and Premium checks. Media downloads require caller-bound authorization on each access. |
| Hosted writes | Add explicit opt-in text and media sends after reads. Use `POST /v1/messages/send`, a bounded `POST /v1/uploads` returning a short-lived caller-owned handle, and `POST /v1/messages/send-media`. Require send scope, deployment enablement, and the active user's write grant. Enforce file type, size, expiry and quotas while streaming uploads. |

Return normal HTTP statuses with a stable error body such as `{"error":{"code":"rate_limited","retry_after_seconds":4}}`. Use 400 for malformed inputs, 401 for invalid credentials, 403 for insufficient scope, 404 for unavailable/foreign objects, 409 for account or linkage conflict, 413 for oversized input, 429 with `Retry-After` for quota, and 503/504 for upstream unavailability/deadline. Whole-operation failures differ from success with per-item errors. Redact upstream diagnostics. Carry send delivery state in errors, including `unknown` with `retryable=false` after ambiguous dispatch. Disable automatic retries for mutations at the gateway, proxy and API. A lost receipt does not authorize a resend. Document the lifetime and caller scope of any recovery facility before exposing it. [Existing receipt semantics](sending.md#receipts-charges-and-uncertain-delivery)

Serve MCP Streamable HTTP at `/mcp` using rmcp's transport and a router separate from the stdio router. Implement protected-resource discovery, bearer challenges, origin validation, request cancellation and bounded responses. Start with the 2026-07-28 binding. Advertise only tested protocol versions and capabilities. Return canonical `structuredContent` and matching text, with self-contained schemas. Keep stable tool names and ID semantics for shared reads. Disclose the authorized catalog through `tools/list` and enforce the same permissions at call time. [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) · [MCP tool contract](tool-contract.md)

| Hosted tool choice | Behavior |
|---|---|
| Initial catalog | `search_messages`, `get_recent_messages`, `get_messages_batch`. Extend access to other reads as their API operations ship. |
| Message links and media | Return links the remote client can open. Offer bounded MCP image blocks or authenticated caller-scoped media resources. Host paths, desktop-launch tools and process-wide response history belong to local stdio. |
| Sending | Advertise only when authorized. Hosted media uses the upload handle. Keep Telegram target validation, receipts and uncertain-delivery rules. |
| Continuous posts | Expose the feed through the Rust core and the HTTPS API. The first MCP catalog uses bounded read tools. An ordinary tool call must finish. A future MCP-native subscription needs a separately negotiated protocol contract. |

For AI-facing clients, the published Telegram API and content terms restrict AI uses and describe possible exceptions tied to specific content and the relevant users' consent. A Telegram account link establishes technical access. Hosted scope configuration must separately represent the permitted content/use. Keep the AI-facing catalog channel-scoped in the first release and enforce the same authorized scope in the API for its delegated calls, including history, batch, and media lookups. Scope selection alone does not establish consent. The operator determines permitted production use before enabling that content. [Telegram API terms](https://core.telegram.org/api/terms) · [Content terms](https://telegram.org/tos/content-licensing)

## Live channel stream

**Transport choice.** Rust callers consume a typed asynchronous receiver in process. External subscribers use SSE because posts flow from server to client and the API already provides HTTPS, authentication, and history reads. WebSockets would add a bidirectional connection protocol useful for changing subscriptions in place. gRPC would add a Protobuf contract and generated clients useful for service-to-service streaming. Subscription filters in v1 are fixed for the life of a connection. A fresh connection changes them. Durable replay would require event retention, client positions, expiry, and acknowledgment rules. The selected live feed uses per-connection memory and lets applications request history when they need it.

**Delivery contract.** Each subscription starts live, including every reconnect. Select one or more explicit channel IDs positively identified as broadcast channels the linked account has joined. Reject the entire subscription if any requested channel is ineligible. Deliver new ordinary channel posts, including media-only posts and the account's own new channel posts. An album emits one event per message with an optional shared album ID. Exclude private dialogs, groups, service messages, edits and deletions. Include typed IDs, UTC publication time, text/caption, and bounded media metadata. Fetch media bytes separately. Within a channel, emit accepted new posts in Telegram order and suppress duplicates for this connection. Cross-channel interleaving follows observation order. The stream is best effort and carries no durable delivery or replay guarantee.

The four required post fields are `channel_id` (decimal string), `message_id` (positive integer), `published_at` (RFC 3339 UTC), and `text` (text or caption, empty for a captionless post). Include `media` as either null or an object with the existing domain media kind and available bounded metadata. An optional `album_id` is a decimal string. Identify a post by account, channel and message ID. Scope duplicate suppression to the current reader/subscription generation. Filters run before a post enters a subscriber's queue.

**Account reader.** A stream-capable client retains the sender's native
update receiver. Run one supervised reader per active streaming account.
Initialize the pinned SDK's message boxes from Telegram's current update
state to start live without offline replay. Keep peer information needed to resolve updates, distinguish broadcasts from supergroups, and reuse existing domain conversion. A listener must neither start a second Telegram connection nor trigger a history poll for every event. Initial membership/head RPCs are bounded and charged once per attempted channel. Bound and account separately for SDK connection maintenance and difference requests. [Current lifecycle](../crates/telegram-core/src/telegram/client/lifecycle.rs) · [Telegram update sequencing](https://core.telegram.org/api/updates)

**Starting boundary.** Define the boundary per channel using a Telegram snapshot of the latest visible message ID. A snapshot of an empty channel uses JSON `null`. Avoid machine-clock comparisons and global message IDs.

1. Authenticate, validate and deduplicate the IDs, admit the subscription, reserve account capacity, and register a bounded pending listener with the single reader **before** requesting the channel heads. Resolve membership and read each authoritative head under one setup deadline. Fail the complete attempt on denial, overflow, timeout or reader-generation change.
2. Atomically install the per-channel heads, enqueue `ready` first, then drain buffered eligible updates strictly above each head and transition to live delivery. Updates accepted during the drain follow them through the same ordered queue. Treat a null head as preceding the first positive ID. Duplicate observations must not produce duplicate events. The heads can be captured at different instants across channels.
3. On reconnect repeat the handshake with fresh heads. Serve new posts regardless of a supplied `Last-Event-ID`. Document this behavior and omit SSE `id:` fields. Use a single authentication/authorization context per connection, terminate on credential expiry, unlink, or observed membership/scope loss, and discard queued unauthorized output before further writes.

The first event is `ready`, followed by zero or more `post` events. In this example, the listener opens when channel 42 has reached message 103.

```text
event: ready
data: {"channels":[{"channel_id":"42","head_message_id":103}]}

event: post
data: {"channel_id":"42","message_id":104,"published_at":"2026-11-19T09:00:00Z","text":"Doors open","media":null}

```

Use `Content-Type: text/event-stream`, private no-store caching, disabled proxy buffering, periodic comment heartbeats, and a bounded socket-write deadline. Authorize bearer clients through headers. Browser clients can use authenticated streaming fetch or a protected same-origin cookie flow. Keep credentials out of URLs. Send HTTP errors before accepting the stream. After `ready`, an observed reader interruption, service drain, or slow consumer ends that subscription. A best-effort terminal `interrupted` event carries a safe reason such as `slow_consumer` or `upstream_disconnected`. EOF also ends continuity. Closing a full queue must complete even when the terminal event cannot be delivered. [SSE framing](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**Loss and capacity.** Bound subscriber queues in bytes and items, including during head capture, and bound each serialized event. Close an overflowing subscriber while continuing service to others. Upstream reader failure closes its generation of subscribers. A supervisor may reopen the account reader with bounded backoff and jitter for new subscriptions. At the current pin the SDK may drop updates on internal overflow, and a Telegram difference that is too long can advance state without yielding the missing posts. Document that limitation. Preserve observable discontinuity signals where the upgraded SDK exposes them. Never infer a lost post solely from a jump in message IDs. Idle streams wait asynchronously for posts, while individual RPCs, writes and shutdown have deadlines.

**Explicit history catch-up.** A consumer can persist its last successfully processed message ID per account and channel. To bridge an absence, connect first and read `ready`. While consuming/buffering live posts within a client-side bound, page through history for `after_id < message_id <= through_id`, where `through_id` is that channel's advertised head. Skip an empty range. The hosted history endpoint accepts an inclusive `through_id` and a separate exclusive `before_id` for older pages. Handle the inclusive bound without overflowing the largest message ID. For this range mode use individual messages, explicit ID bounds instead of an implicit time window, newest-first pages, and a per-channel continuation. Reorder historical pages before processing when chronological delivery matters. Historical queries reflect messages still accessible at read time. If the client buffer overflows, start again from the last processed ID. Stdio retains its documented exclusive cursor semantics. The service stores neither consumer offsets nor an event archive.

**Proposed starting limits.** Use configurable deployment defaults of 20 channels per subscription, 4 subscriptions per account, 64 active account clients, 256 total subscriptions, and 128 events or 1 MiB per subscriber queue, whichever fills first. Cap encoded events at 64 KiB, send a heartbeat every 15 seconds, and cap a stalled write at 10 seconds. Count queued bytes against a service-wide ceiling of 64 MiB. Expose setup timeout, idle eviction, and total in-flight requests as bounded settings. Keep metrics aggregate (active readers, subscribers, queue bytes, rejections and interruption reasons). Exclude message bodies, phone numbers, codes, tokens and session material from logging and metric labels.

## Dependency upgrade milestone

Upgrade **all project libraries** against a fresh UTC-dated upstream inventory when implementation begins. Recheck the complete workspace at final integration so libraries introduced by the service work are covered too. The previous dependency report is useful for provenance, but its version numbers are a historical snapshot. [Previous inventory](dependency-status.md) · [Maintenance policy](maintenance.md)

1. Capture the current locked graph with `cargo metadata --locked --format-version 1`, dependency kinds, features, targets, duplicates, source revisions and a passing baseline. Include normal, optional, target-specific, build, development, example/test dependencies, and the full transitive graph across workspace members.
2. Compare each registry library with its newest published **stable, non-yanked** release. Update direct manifest requirements across major and pre-1.0 breaking lines as needed, migrate callers, and resolve the existing lockfile in reviewable dependency families. A plain lockfile update can remain inside an old manifest range. Adopt current stable versions for newly added libraries. The approved temporary rmcp revision makes Chrono optional. Return to a stable crates.io release when it can pass the same Chrono-free graph and transport checks. [Cargo update](https://doc.rust-lang.org/cargo/commands/cargo-update.html) · [Cargo version requirements](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)
3. For the Git-sourced grammers family, inspect current official Codeberg upstream, migrate to the latest upstream revision at the inventory cutoff and pin all three direct crates to that same full SHA. Review generated TL changes, update handling/overflow, sender lifecycle, SQLite sessions and their sidecars, peer identity, media and send behavior. Verify the resolved grammers packages share that revision. Keep the checked-in lockfile throughout.
4. Refresh transitive packages to their latest resolvable stable releases. Where a newer transitive line is excluded, try the current parent first, identify the exact blocking parent/constraint with `cargo tree -i`, and list duplicates and their reasons. Document the exact blocker and impact for any direct library that cannot reach latest after migration and report it as an open upgrade. Update the timestamped dependency report with old/resolved/latest versions, sources, breaking migrations, and evidence for every exception. Keep source, license and advisory checks effective for the full graph.
5. Run the macOS quality gate, offline stdio/legacy fixtures, previous-session migration fixtures, release builds, dependency policy fixtures, and fresh advisory/source checks. For rmcp explicitly verify both existing stdio protocols and the new Streamable HTTP transport. Follow the existing toolchain and CI maintenance policy if a verified library minimum requires a toolchain change. A dependency upgrade is separate from a connector version bump or release.
